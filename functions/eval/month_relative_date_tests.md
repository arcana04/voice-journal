# Month-based relative date extraction — new gap ("next month" / "in N months" / "on the 1st")

## Background

`due_weekday` (weekday-based), `relative_offset_minutes` (pure clock-relative), `span_days`
(multi-day spans), and `recurrence` (repeating weekday patterns) all got moved out of the model's
own arithmetic into deterministic code in rounds 7–11 (see `round9_timing_and_classification_tests.md`
and the app-wide bug audit). Month-based relative expressions never got the same treatment — "next
month", "in 3 months", "on the 1st" are still left to the model computing the date itself. Given the
same failure pattern kept showing up for every other date-math category (wrong result, or same input
producing a different result on repeat), this file exists to actually observe what currently happens
before writing a `due_month` field + deterministic resolver.

**How to run:** device language = English, no category filter chip selected. Type each transcript
into the text-input fallback (NOT voice — keeps the transcription variable out of it), then record
what actually came out (due date, all-day vs timed). Mark: ✅ match / ⚠️ partial / ❌ wrong.

**Reminder from the 9/22 deploy gotcha:** the text-input fallback calls `processTextMemo`, a
separate Cloud Function from `processVoiceMemo` that happens to share the same prompt code. If a
fix is deployed here later, deploy both:
`firebase deploy --only functions:processVoiceMemo,functions:processTextMemo`.
