## Part D — timed multi-day events (span_days + reminder_at/reminder_end_at, new)

The span_days rule (added 2026-09-22 for all-day multi-day spans like "Friday through Sunday")
only says reminder_at/reminder_end_at stay null "unless a specific time is mentioned" — there is
no rule at all for what should happen when a multi-day span ALSO has an explicit time (e.g. "9am
Monday to 5pm Wednesday"). due_date_end is computed deterministically from span_days for the
all-day case, but nothing computes an end *date+time* the same way, so the model would have to
self-calculate that combination — the same kind of arithmetic that has caused bugs everywhere else
it wasn't offloaded to code. Suspect this either silently drops the time, drops span_days entirely,
or produces a reminder_end_at with the wrong date.

## Part E — overnight / midnight-crossing time ranges (reminder_end_at date advance, new)

Traced through the code for this one before writing tests: `resolveTaskDueWeekday` unconditionally
forces reminder_end_at's *date* to match the task's start date (due_date) whenever due_weekday is
used — so if the model correctly wrote a next-day end time for an overnight event, that gets
flattened back onto the start day. However, the final response-building step has an existing safety
net (`if reminder_end_at <= reminder_at, try advancing it by one day`) that happens to re-derive the
correct next-day date afterward — so a plain overnight event should actually survive, by accident of
two bugs cancelling out. What's NOT covered by that accident: combining an overnight end time with
the new span_days multi-day logic. My 2026-09-22 fix forces reminder_end_at's date to `due_date_end`
(the last spanned day) whenever span_days is set — but if the event's end time crosses PAST midnight
of that last spanned day (e.g. a Friday-to-Sunday trip that doesn't actually wrap up until 1am
Monday), the correct end date is due_date_end **+1**, not due_date_end itself, and nothing computes
that. E03 below targets exactly this.
